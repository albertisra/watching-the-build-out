## Details

### Archive structure and download
The archive holds "pro Objekttyp eine XML-Datei" [2]. Large objects are split: "Wenn die XML-Datei eines Objektes eine gewisse Größe überschreitet, z.B.: 100.000 Zeilen ... wird eine neue Datei erstellt" and files are numbered consecutively [2 p.16]. The spec example names the split files `Solareinheiten_1.xml` while the object tables name the file `EinheitenSolar.xml`; expect `EinheitenSolar_1.xml`, `_2.xml`, ... in practice (UNVERIFIED, no archive opened). Catalogue values (status, PV type, battery technology, etc.) are integer IDs resolved through `Katalogwerte.xml` and `Katalogkategorie.xml` [2 p.31-32]. Because the file name changes daily, a loader must read the current link from the download page [1]; the `open-mastr` package does this (see below).

Special fields: attributes with suffix `_nv` ("nicht vorhanden") mean the owner declared the value does not exist; when true, ignore the value in the main attribute [2 p.31]. "Nicht jedes Pflichtfeld ... ist im Gesamtdatenexport enthalten. Dies kann auf rechtliche Gründe wie Betriebsgeheimnisse oder Datenschutzgründe zurückzuführen sein" [2 p.31].

### Licence and reuse
Download page: licence "Datenlizenz Deutschland – Namensnennung – Version 2.0" [1]. Impressum: data in .xls/.csv and from the web service fall under that licence "unless marked otherwise"; "Alle darüber hinausgehenden Handlungen bedürfen einer vorherigen schriftlichen Zustimmung der Bundesnetzagentur" [3]. The licence text [5] allows commercial and non-commercial use, and that data may be "vervielfältigt, ausgedruckt, präsentiert, verändert, bearbeitet sowie an Dritte übermittelt werden". Conditions: source note with provider name, licence name/URI (www.govdata.de/dl-de/by-2-0) and dataset reference, and "mit dem Hinweis zu versehen, dass die Daten geändert wurden" for modified data [5]. Consequence: derived and aggregated data may be republished (also in a public GitHub repo) with attribution and a "modified" notice. The Zenodo datapackage of open-mastr uses the attribution form "© Marktstammdatenregister 2021 | dl-de/by-2-0" [14]; a provider-prescribed attribution string for the export was not found (open question).

Status codes seen in BNetzA filter links [4]: `Betriebs-Status eq '35'` is used for "In Betrieb"; `'35,31'` is used for "In Betrieb oder In Planung", so 31 is very probably "In Planung" (inferred, UNVERIFIED; always resolve through `Katalogwerte.xml`). The pre-reform PV type "Freifläche" had ID 852 in that guide (Aug 2025); IDs may have been reassigned by the 01.10.2025 catalogue change, so do not hard-code.

PV type reform: before 01.10.2025 six values (Steckerfertige Solaranlage, Bauliche Anlagen (Hausdach, Gebäude und Fassade), Bauliche Anlagen (Sonstige), Freifläche, Gewässer, Großparkplatz); since then four, with ground-mounted = "Freiflächensolaranlage" defined as "mittels einer ausschließlich für die PV-Anlage errichteten Unterkonstruktion mit der Erdoberfläche (Boden, Gewässer) verbunden"; this includes landfills, gravel pits and floating PV [15], [16]. "Sonstige Solaranlage" covers noise barriers and large car-park canopies. Floating PV and landfill PV therefore fall into the ground-mounted class and cannot be separated by this field alone. The BNetzA slides say for the area field: "Bilden mehrere Solareinheiten einen Solarpark, so ist für die Einheit nur die anteilige Fläche am Solarpark einzutragen" [16]. Many parks are therefore several units; group them by `LokationMaStRNummer` or `NameDesSolarparks`. The area fields were removed in the data migration ("Angaben zu Flächendaten wurden für diese Migration entfernt" per a search summary of [16], SECONDARY).

### Coordinate publication rule
- Legal basis: MaStRV §15(1) Nr.1 a [8]: not published are "Standortangaben (Straße, Hausnummer, Flurstücke, Geokoordinaten)" for generation units in tables B to E up to 30 kW (this wording is a tool paraphrase; the page quote limit prevented a verbatim copy; the Anlage [9] confirms with legend "V*1: vertraulich nach Maßgabe von § 15 Absatz 1 Satz 1 Nummer 1 Buchstabe a (Einheiten ≤ 30 kW)", applied to B.1.1.2 address/parcel and B.1.1.3 "Standort der Einheit (geografisch)").
- So the threshold is "≤ 30 kW confidential", i.e. units > 30 kW should have published coordinates *if the operator entered them*. Coordinates are an optional field in the export (Pflicht "Nein") [2]. The preprint [13] states "units larger 30 kWp have exact coordinates and an address" in one section and "up to 30 kW" in another (inconsistent), and reports coordinate completeness per technology in its Table 3 as wind 97 %, biomass 96 %, hydro 55 %, combustion 26 %, solar 5 %, storages 0 % (snapshot March 2024, all sizes). The solar figure is plausible because most units are small; **the 0 % for storages is not explained** in the text and conflicts with the legal rule. Whether utility-scale storage units > 1 MW carry coordinates in the current export must be checked empirically on the first download (open question).
- Natural persons: data on market actors (name, address, birth date, etc.) are not published if the actor is a natural person (§15(1) Nr.2; Anlage legend V*3) [8], [9]. The unit's location fields are not affected by this rule; they follow the 30 kW rule. We do not collect operator identity of natural persons.
- Aggregation: operators of several generation units at common grid connection points may ask for aggregated publication, but "die Zusammenfassung ... ist nicht anzuwenden auf Einheiten, die zu EEG- und KWK-Anlagen gehören" [8]. Non-EEG storage units may therefore appear merged.
- Critical infrastructure (BSI-KritisV) units can be exempted on request [8].
- Trend to watch: release notes show further withdrawal of location data: 26.1.195 (17.09.2026) "Daten werden nicht mehr veröffentlicht bei Verbrennungseinheiten mit einer Nettonennleistung >= 10MW" (portal, web service and data download); 26.2.198 (29.10.2026) "Entfernung der Standortattribute" from the "Aktuelle Einheitenübersicht" for generation, grid connection points and locations (not technology-limited; export not named); 26.2.200 (26.11.2026, announced) removes location attributes from two web-service functions for grid connection points [7]. None of these explicitly names solar or storage in the bulk export, but the direction is toward less location data. Re-check the export schema before each use.
- Doc example inconsistency: the export documentation's example row lists `Laengengrad` = 51.254 and `Breitengrad` = 12.597 (swapped relative to Germany: lat about 47-55, lon about 6-15) [2 p.55, 95]. It is only an example, but a loader should sanity-check that Breitengrad lies in 47-56 and Laengengrad in 5-16, and swap if reversed.

### Status and history
- The export is a current-state snapshot with a per-object timestamp `DatumLetzteAktualisierung`/"LetzteAenderung" [2 p.30]. No status history table exists. History can only be reconstructed by (a) quarterly snapshots at the Stichtage (kept online; "historical download archives" were temporarily removed 17.09.2026 and restored 29.10.2026 [7]), (b) our own daily archive, (c) date fields (`Registrierungsdatum`, `GeplantesInbetriebnahmedatum`, `Inbetriebnahmedatum`, shutdown dates).
- Units can be set back to "in Planung" by a status correction ("Wenn der Betriebsstatus durch die Korrektur als 'in Planung' registriert wird, müssen Sie die Einheit erneut 'in Betrieb' registrieren", per search summary of a BNetzA manual, SECONDARY) and release note 22.2.101 confirms re-registration after correction to "in Planung" [7]. Therefore a snapshot can show a unit going backwards in status.
- Deleted/deactivated units are exported separately with deletion date and reason [2 p.140].

### Known data-quality issues
From Kotthoff et al. [13] (preprint, snapshot 12.03.2024): district/municipality mismatch with coordinates (1.5 km buffer) for more than 3 % of wind units, 0.5 % to 2 % for other technologies; about 2.9 GW of solar with municipality mismatch; PV inverter vs module power differing by a factor of 20 or more for 23,251 units (0.6 %); module count outside 50-700 W per module for 43,733 units (1.12 %), many with one module "possibly as a placeholder"; ground-mounted PV outside 0.05-1.5 MW/ha for 21.3 % (3,758 units); installation years before 1980 for 287 storages and 1,169 PV systems (e.g. a battery with year 1923); 6 storages with inverter power above net power; commissioning date completeness 98 % for solar. Authors: the grid operator must validate capacity and address but not the coordinates; "many location errors passed these checks unnoticed". Headline number in the search summary (15 % of PV systems at wrong location by manual aerial-image check) comes from an earlier version of the same arXiv paper (title "Improving Data Reliability ... A Validation of Unit Locations") and was not re-read in v2 (SECONDARY).
Not found in any source opened: coordinate rounding statistics, duplicate rates, or a documented share of "Netzbetreiberprüfung" verified units. `NetzbetreiberpruefungStatus` is mandatory in the export (values via catalogue "Status der Netzbetreiberprüfung") but the meaning of each value was not retrieved. The open-mastr Zenodo record warns "Data may contain duplicates" [12]. Release notes show repeated fixes to storage capacity validation (26.1.185, 30.04.2026: "Fixes usable storage capacity validation. Changes the inverter power limit for battery storage") [7], which means older capacity values may have been entered under different validation ranges.
Registration lag: operators have one month after commissioning [4]; and the commissioning date is entered by the operator (self-reported). The new field `InbetriebnahmedatumAmAktuellenStandort` (25.2) exists for relocated units.

### open-mastr (OpenEnergyPlatform)
Python package that "downloads the daily MaStR dumps in bulk ... and parses the XML files into a local relational database", also wraps the SOAP web service and can export CSV; `english=True` translates table and column names [17]. Tables: `units_solar`, `units_electricity_storage`, `installations_eeg_solar`, `installations_eeg_storage`, `installations_electricity_storage` (a locations table exists in the German schema, `Lokationen` [19], English name unverified) (German names `EinheitenSolar`, `EinheitenStromSpeicher`, `AnlagenEegSolar`, `AnlagenEegSpeicher`, `AnlagenStromSpeicher`, `Lokationen`) [18], [19]; the "Anlagen" tables hold `VerknuepfteEinheitenMaStRNummern`. Since v1.0.0 CSV export no longer joins unit, CHP/EEG and permit data [18]. Package licence AGPL-3.0-or-later (PyPI JSON) [11]; data licence dl-de/by-2.0 [17]. Latest version 1.1.0 (2026-11-06), Python >= 3.12 [10], [11]. It "does not edit or change the data" [18]. Zenodo: CSV/zip dumps at 10.5281/zenodo.6807425; newest 2025-02-09 [12], too old for our purpose (use only for schema experiments); the page [18] says the pipeline runs only "occasionally". AGPL note: importing the package in our own public repository is fine, but distributing a modified copy or offering it as a network service triggers AGPL obligations; do not copy its code into a differently licensed repo without checking.

### OSM tagging (OSM wiki)
- `power=plant`: area/multipolygon, not nodes or ways; "An industrial facility where power ... is produced by individual power generator units". Keys: `plant:source` (e.g. `solar`, `battery`, semicolon list), `plant:output:electricity` (e.g. 24 MW), `plant:method`, `plant:storage` (rated storage capacity), `name`, `operator`, `start_date`. Large solar parks: multipolygon tagged `power=plant`, `plant:source=solar`, `plant:output:electricity`; modules/arrays as `power=generator`. Guideline: "generators under 1 MW normally shouldn't be tagged as power plants" [20].
- Battery storage [21]: grid battery packs `power=generator` + `generator:source=battery`, `generator:method=battery-storage`, `generator:type=lithium_ion`, `generator:output:electricity=xx MW`, `generator:storage=xx MWh`; container: `building=container`. Dedicated facility: `power=plant` + `plant:source=battery`, `plant:type=lithium_ion`, `plant:output:electricity`, `plant:storage=xx MWh`, area.
- `power=substation` [22]: facility "with transformers, switchgear or compensators"; usually an area; `substation=transmission|distribution|minor_distribution|...`; `voltage=` highest first (e.g. `400000;225000;63000`). The page does not mention battery sites.
- Dispersed generators without a perimeter use a `type=site` relation [20].
- Licence: ODbL. "If you alter or build upon our data, you may distribute the result only under the same license" [23]; attribution must name OpenStreetMap, e.g. "Map data from OpenStreetMap" or "© OpenStreetMap contributors", ideally linking to openstreetmap.org/copyright [24]; "Attribution is only required when a Produced Work is used publicly"; a "substantial extraction" used as a dataset is a Derivative Database and "must be available on ODbL terms if used publicly"; "predictions made by the model are not implicated by the ODbL" [24]. Practical consequence: a public repo containing an OSM extract (e.g. site polygons) must be released under ODbL; we should keep OSM-derived geometry in a separate, ODbL-labelled file and keep MaStR-derived data (dl-de/by-2-0) separate from it.

## What this means for our method
- Build the registry table by joining: `EinheitenStromSpeicher` -> `AnlagenStromSpeicher` (via `SpeMaStRNummer`) for kWh; `EinheitenSolar` filtered on `ArtDerSolaranlage` = Freiflächensolaranlage; both -> `Lokationen` -> `Netzanschlusspunkte` for voltage level and grid operator. Resolve all catalogue IDs from `Katalogwerte.xml` of the same export version; never hard-code IDs.
- Our size thresholds (BESS from 1 MW, solar from 1 MWp) should use `Bruttoleistung` for BESS (BNetzA "Großbatteriespeicher" is > 999 kW gross) and `Nettonennleistung` for solar; report both, and note solar `Bruttoleistung` vs `Nettonennleistung` differ (module vs inverter).
- Park aggregation: one park is often several units (area field is "anteilige Fläche"); aggregate by `LokationMaStRNummer`/`NameDesSolarparks` before comparing with an image-derived park footprint. Floating PV and landfill PV are inside "Freiflächensolaranlage".
- Timing comparison: use `GeplantesInbetriebnahmedatum` (planned), `Registrierungsdatum` (registered), `Inbetriebnahmedatum` (commissioned, self-reported, registration allowed up to one month later), and our own daily/quarterly snapshots to capture status changes, since the export keeps no history. Start archiving the daily export now.
- Coordinates: expect many large units to lack or have inaccurate coordinates (about 2-3 % wrong municipality for non-wind, possibly more, plus lat/lon swaps in docs examples). Fall back to Gemeinde/PLZ polygons as search areas; treat MaStR point as a hint, not ground truth. Check first whether large BESS rows have non-null `Breitengrad`.
- Policy risk: BNetzA is withdrawing location attributes (26.1.195, 26.2.198, 26.2.200). Add a schema/coverage check to the loader and keep a dated copy of each snapshot we use.
- Licence: publish aggregated results with "© Bundesnetzagentur, Marktstammdatenregister, dl-de/by-2-0, data modified" (confirm exact form with the provider) and keep OSM-derived data under ODbL.
